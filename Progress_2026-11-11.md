## Pending rules, unchanged by this update

1. Latest Task3 slide 26 says any withdrawal requires all remaining members to reconfirm. Current implementation retains valid consent unless a material plan edit occurs. Slide 27 also has contradictory WAITING wording for groups of two or more. Keep current code until the group confirms the rule.
2. Task3 uses RECONFIRMATION_REQUESTED and RECONFIRMATION_REQUIRED, plus EXPIPED. Existing API uses RECONFIRMATION_REQUIRED and EXPIRED. Do not rename API enums merely to match a slide typo.
3. Task3 broadly says cancellation/expiry can occur at any stage, but other slides restrict cancellation to pre-start states. Current code rejects cancellation after departure and does not cancel an ongoing/completed ride.
4. The 60-minute overlap interval and 30-minute confirmed-ride start grace are prototype defaults, not newly approved rules.
5. Task2 Appendix A.3 retains review of service points and configured defaults: tolerance, invitation deadline, late cancellation warning, capacity, retention and quality targets. Keep values until confirmed.
6. DFD mentions member/chat information, while Task2 explicitly defers in-app chat. Do not implement chat without a scope decision.
